Documentación técnica

Watermelon DDNS

Clon propio de NO-IP DUC: cada trabajador de Watermelon Marketing tiene un subdominio (nombre.watermelonmarketing.com) que una app de escritorio mantiene apuntando a su IP pública, sin depender del binario Intel-only que Apple dejó de soportar.

repo: watermelonnoip · branch main carpeta: ~/Desktop/LABS/NOIPPROPIO generado: 2026-08-27

Resumen ejecutivo

Qué es esta app, por qué existe y cómo encajan sus piezas.

Motivo: NO-IP DUC dejó de compilar como app universal para Mac — Apple avisa de "fin de compatibilidad con apps para Intel" en su binario. En vez de depender de un cliente de terceros, Watermelon Marketing tiene ahora su propio DDNS: una app de escritorio (Tauri v2 + React) que vigila la IP pública de cada equipo y la publica en Cloudflare DNS bajo el dominio propio watermelonmarketing.com.

Cada trabajador recibe un subdominio dedicado (samuel.watermelonmarketing.com, fernando.watermelonmarketing.com...) y un token opaco generado por el admin. La app nunca ve ni guarda credenciales de Cloudflare — solo ese token, que el backend intermedio traduce a la llamada real contra la API de Cloudflare.

  • Plataformas: macOS (universal Intel + Apple Silicon), Windows, Linux — vía Tauri.
  • Login: pantalla única, se pega el token una vez y queda guardado en el localStorage del WebView de ese equipo.
  • Detección de IP: polling cada 5 minutos contra api.ipify.org (con dos servicios de respaldo). Solo llama al backend si la IP cambió.
  • Backend intermedio obligatorio: el token de Cloudflare con permiso de editar DNS nunca sale del servidor. Si se filtra el instalador o el token de un trabajador, solo compromete su propio registro DNS.
Estado actual Backend en producción en xwmkt, verificado con curl -i https://ddns.xwmkt.com/health → 200. App con identidad de marca de Watermelon Marketing (ver Identidad de marca), icono de bandeja del sistema (ver Bandeja del sistema), CI multiplataforma en GitHub Actions y un endurecimiento de seguridad — token fuera de localStorage y CSP activa (ver Endurecimiento de seguridad).

Arquitectura

Los tres saltos de red que hacen que una IP casera acabe siendo un registro DNS público.

  • Host del backend: xwmkt (IP 49.13.140.132), acceso root@xwmkt.com -p50050.
  • Stack backend: Node 20 Alpine, Express 4, better-sqlite3 11, fetch nativo de Node 18+, CORS abierto.
  • Base de datos: SQLite en /opt/ddns-backend/data/ddns.db, montada como volumen /app/data en el contenedor.
  • Dominio del backend: ddns.xwmkt.com → Nginx Proxy Manager (jc21/nginx-proxy-manager) → contenedor xwmkt_ddns-backend_1:3000. Certificado Let's Encrypt (DNS-01 / proxy Cloudflare).

Backend

Node 20 + Express 4 + SQLite. Un único archivo de estado: la tabla workers.

Esquema de base de datos

Definido en server/src/db.js. Se crea automáticamente si no existe, en server/data/ddns.db (en producción, /opt/ddns-backend/data/ddns.db, montado como volumen Docker).

SQLserver/src/db.js
CREATE TABLE IF NOT EXISTS workers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  subdomain TEXT UNIQUE NOT NULL,   -- ej. "samuel"
  token TEXT UNIQUE NOT NULL,       -- hex de 64 caracteres (32 bytes aleatorios)
  last_ip TEXT,
  cf_record_id TEXT,                -- id del registro A en Cloudflare (se cachea tras el primer update)
  updated_at DATETIME
);

Endpoints de la API

Definidos en server/src/index.js. Todos (salvo /health) requieren cabecera Authorization: Bearer <token>; el middleware getWorkerFromReq busca ese token directamente en la tabla workers — si no hay fila, 401.

MétodoRutaAuthRespuesta
GET /health — {"status":"ok"} — para healthchecks de NPM/monitorización.
GET /api/status Bearer token {success, worker_name, subdomain, last_ip, updated_at} o 401 {"error":"Token inválido"}.
POST /api/update-ip Bearer token body {ip}. Ver flujo detallado abajo.

Flujo de POST /api/update-ip:

  1. Valida el token y resuelve el trabajador.
  2. Si el trabajador no tiene cf_record_id guardado, llama a getOrCreateRecord() para buscar o crear el registro A en Cloudflare y lo cachea en la fila.
  3. Si la IP recibida es igual a last_ip, responde {"status":"unchanged"} sin tocar Cloudflare.
  4. Si cambió, llama a updateRecord() (PUT a Cloudflare), actualiza last_ip y updated_at, y responde {"status":"updated"}.
CORS Access-Control-Allow-Origin: *, Allow-Headers: Content-Type, Authorization, Allow-Methods: GET,POST,OPTIONS — necesario porque el WebView de Tauri llama desde el origen tauri://localhost. En un endurecimiento futuro podría restringirse a ese origen exacto.

Integración con Cloudflare

En server/src/cloudflare.js. Lee tres variables de entorno: CF_API_TOKEN, CF_ZONE_ID, DOMAIN (por defecto watermelonmarketing.com), cargadas desde /opt/ddns-backend/.env (permisos 600, nunca en Git).

FunciónQué hace
cfFetch(url, opts)Wrapper de fetch con el header Authorization: Bearer CF_API_TOKEN; si success:false, lanza un error con el mensaje que devuelve Cloudflare (p. ej. Authentication error si el token es inválido).
getOrCreateRecord(subdomain, ip)GET busca un registro A para subdomain.watermelonmarketing.com; si no existe, POST lo crea con ttl: 120, proxied: false.
updateRecord(recordId, subdomain, newIp)PUT a /zones/<ZONE_ID>/dns_records/<id> con la IP nueva.

El registro se crea siempre con proxied: false (DNS-only) — un router doméstico expuesto directamente, sin pasar por el proxy naranja de Cloudflare.

Docker

better-sqlite3 compila un módulo nativo, así que hace falta una etapa de build con herramientas de compilación — pero esas herramientas no deberían viajar en la imagen final. Desde el endurecimiento de agosto 2026, el build es de dos etapas:

Dockerfileserver/Dockerfile
# Etapa de build: aquí sí hacen falta python3/make/g++ para compilar better-sqlite3
FROM node:20-alpine AS builder
WORKDIR /app
RUN apk add --no-cache python3 make g++
COPY package.json ./
RUN npm install --omit=dev
COPY . .

# Etapa final: imagen limpia, sin toolchain de compilación, sin usuario root
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app ./
RUN chown -R node:node /app
USER node
EXPOSE 3000
CMD ["node", "src/index.js"]

En docker-compose.yaml (host xwmkt) el servicio monta /opt/ddns-backend/data como volumen /app/data y solo expone el puerto 3000 internamente (expose, no ports) — la única entrada pública es vía Nginx Proxy Manager.

Paso manual obligatorio antes de redesplegar El contenedor ahora corre como el usuario node (uid 1000), no como root. Si /opt/ddns-backend/data en el host pertenece a root (lo normal, se creó con mkdir por SSH), el contenedor nuevo no podrá escribir ddns.db y el backend fallará al arrancar. Antes de hacer docker-compose up -d --build ddns-backend, ejecuta una vez en xwmkt:
bashen xwmkt, una sola vez
chown -R 1000:1000 /opt/ddns-backend/data

CLI de administración

server/cli.js, se ejecuta dentro del contenedor. Gestiona altas, bajas, rotación y consulta de trabajadores directamente sobre la base SQLite.

bashdentro del contenedor xwmkt_ddns-backend_1
node cli.js add "Samuel" samuel   # crea el trabajador, imprime su token una vez
node cli.js list                  # tabla id / name / subdomain / last_ip / created_at / updated_at
node cli.js token samuel          # reimprime el token de un trabajador existente
node cli.js rotate samuel         # genera un token nuevo; el anterior deja de servir al instante
node cli.js remove samuel         # elimina el trabajador (revoca su acceso)

El token se genera con crypto.randomBytes(32).toString("hex") — 64 caracteres hexadecimales, único por columna UNIQUE en la tabla. La tabla guarda también created_at (fecha de alta del trabajador) para poder auditar tokens antiguos con list y decidir cuándo rotarlos a mano.

Endurecimiento del backend (agosto 2026)

  • Rate limiting: express-rate-limit en todo /api/*, 30 peticiones por IP y minuto. La app solo llama cada 5 minutos (o al pulsar "Actualizar ahora"), así que no afecta al uso normal, pero corta de raíz cualquier martilleo del endpoint.
  • CORS ya no es * sin más: se restringe a los orígenes reales del WebView de Tauri — tauri://localhost, y también http://tauri.localhost/https://tauri.localhost, que es el origen que usa Windows y que una CORS mal configurada rompería silenciosamente solo en ese sistema operativo. Peticiones sin cabecera Origin (curl, healthchecks) no se ven afectadas — CORS es una restricción de navegador, no de servidor.
Por qué esto era de riesgo bajo incluso antes La autenticación va por cabecera Bearer, no por cookie — un CORS abierto no permite a una web maliciosa "robar" la sesión de nadie, porque el navegador no adjunta el token automáticamente como sí haría con una cookie. Aun así, restringir el origen es una capa extra de higiene sin coste para el uso legítimo.

App cliente (Tauri + React)

Una sola pantalla que hace tres cosas: guardar el token, sondear la IP y mostrar el estado.

Stack: React 19, @tauri-apps/api v2, @tauri-apps/plugin-opener, Vite 7. Sin librería de estado externa — todo vive en useState/useEffect dentro de App.jsx.

Constantes y lógica de IP

jsxapp/src/App.jsx
const API_BASE = "https://ddns.xwmkt.com";
const IP_SERVICES = [
  "https://api.ipify.org?format=json",
  "https://icanhazip.com",
  "https://ifconfig.me/ip",
];
const POLL_MINUTES = 5;

getPublicIp() recorre IP_SERVICES en orden con cache: "no-store", intenta parsear la respuesta como JSON ({"ip": "..."}) y si falla la trata como texto plano validado con una regex de IPv4 (o presencia de : para IPv6). Si los tres servicios fallan, lanza un error que acaba en el banner rojo de la UI.

Estado y flujo

PiezaRol
token / localStorage.ddns_tokenPersiste el token entre reinicios de la app.
saveToken()Valida que no esté vacío, lo guarda y dispara el primer fetchStatus + doUpdate.
logout()Borra el token, limpia el intervalo de polling.
fetchStatus(token)GET /api/status — rellena la tarjeta de estado.
doUpdate(token)Obtiene la IP, POST /api/update-ip, añade una línea al log clasificada como success o err.
useEffect([token])Al iniciar sesión: fetchStatus + doUpdate inmediatos, luego setInterval cada POLL_MINUTES * 60000 ms.

Los logs se guardan como objetos {ts, msg, type} (máx. 50, los más nuevos primero) y el componente <StatusPill error busy> muestra "Al día" / "Actualizando" / "Error" según el estado de la última operación.

Bandeja del sistema (tray)

Implementado en src-tauri/src/lib.rs. La app añade un icono en la bandeja del sistema con un menú (IP actual, subdominio, última IP, "Actualizar ahora", "Abrir Watermelon DDNS", "Salir") y cambia el comportamiento de cierre de ventana:

  • Cerrar la ventana no cierra la app — el evento WindowEvent::CloseRequested se intercepta, la ventana se oculta (window.hide()) y se cancela el cierre real (api.prevent_close()). La app sigue viva en segundo plano, sondeando cada 5 minutos. Solo Salir desde el menú de la bandeja la termina de verdad.
  • Sincronización con la UI: el comando update_tray(ip, subdomain, last_ip) se invoca desde App.jsx cada vez que cambian el estado o la IP actual, y actualiza el texto de las tres primeras entradas del menú.
  • "Actualizar ahora" desde la bandeja: el clic en esa entrada emite el evento tray-update desde Rust; App.jsx lo escucha con listen("tray-update", ...) y dispara el mismo doUpdate() que el botón de la ventana.
  • Un clic izquierdo sobre el icono de la bandeja alterna mostrar/ocultar la ventana principal.
Importante para los trabajadores Como la app sigue corriendo tras cerrar la ventana, conviene que sepan que verla en la bandeja del sistema es normal — es justo lo que hace que la actualización automática cada 5 minutos siga funcionando en segundo plano.

Endurecimiento de seguridad (agosto 2026)

Tras revisar el modelo de seguridad de la app, se cerraron dos huecos concretos sin tocar el modelo de arquitectura (el token de Cloudflare sigue sin salir nunca del backend — ver Arquitectura):

Token fuera de localStorage

Antes, el token del trabajador se guardaba con localStorage.setItem, dentro del almacén del propio WebView — accesible desde cualquier JavaScript que corriera en esa página (por ejemplo, herramientas de desarrollo o una dependencia comprometida). Ahora se guarda con tauri-plugin-store, un archivo (secure-store.json) en el directorio de datos privado de la app, fuera del alcance del localStorage del navegador.

Precisión importante Esto no es cifrado a nivel de sistema operativo (no usa el Llavero de macOS ni el Credential Manager de Windows) — es un archivo JSON en texto plano, simplemente fuera del almacenamiento del WebView. Sigue siendo un paso real hacia adelante (deja de ser legible con las herramientas de depuración del propio WebView, o por cualquier script que corra dentro de la página), pero si se quiere protección a nivel de Llavero del sistema, sería un paso adicional — usar el Llavero/Credential Manager nativo desde Rust — que conviene implementar y probar directamente en macOS/Windows/Linux antes de confiar en él, en vez de añadirlo a ciegas.

La app migra automáticamente el token de instalaciones anteriores: al arrancar, si no hay nada en el nuevo store pero sí en el localStorage antiguo, lo copia y borra el rastro viejo — el trabajador no tiene que volver a pegar el token.

Content-Security-Policy activa

La app tenía "csp": null en tauri.conf.json — sin ninguna política que limitara qué puede cargar o a qué puede conectarse el WebView. Ahora:

jsonapp/src-tauri/tauri.conf.json
"csp": "default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self' ipc: http://ipc.localhost https://api.ipify.org https://icanhazip.com https://ifconfig.me https://ddns.xwmkt.com"

Solo puede cargar sus propios recursos, las fuentes de Google Fonts, y conectarse por red exactamente a los dominios que la app necesita (los tres servicios de IP y el backend) más el canal interno ipc: que usan invoke()/listen() y el plugin de store. Cualquier otro destino queda bloqueado por el propio WebView, no solo por buenas intenciones del código JS.

Qué cambió, archivo por archivo

  • src-tauri/Cargo.toml — añadida la dependencia tauri-plugin-store = "2".
  • src-tauri/src/lib.rs — registrado .plugin(tauri_plugin_store::Builder::new().build()).
  • src-tauri/capabilities/default.json — añadido el permiso "store:default".
  • src-tauri/tauri.conf.json — CSP explícita (arriba).
  • package.json — añadida la dependencia JS @tauri-apps/plugin-store.
  • src/App.jsx — saveToken/logout ahora escriben en el store; un efecto de arranque migra el token antiguo y muestra "Cargando…" mientras tanto.
Un paso manual, una sola vez Al añadir una dependencia JS nueva (@tauri-apps/plugin-store), hace falta ejecutar npm install dentro de app/ una vez antes del próximo npm run tauri build — si no, Vite no encontrará el paquete. La dependencia de Rust (tauri-plugin-store) la descarga cargo solo, sin pasos extra.

Build multiplataforma automático (GitHub Actions)

.github/workflows/build.yml compila los tres binarios en paralelo cada vez que se hace push a main (o manualmente con "Run workflow"): macOS universal, Windows (x86_64-pc-windows-msvc) y Linux (x86_64-unknown-linux-gnu, con libwebkit2gtk-4.1-dev, libappindicator3-dev, librsvg2-dev y patchelf instalados en el runner). Cada job sube sus instaladores como artefacto de la Action — ya no hace falta tener Windows o Linux a mano para generar esos paquetes.

Un segundo job, audit, corre en paralelo y revisa dependencias en busca de vulnerabilidades conocidas: npm audit sobre app/ y server/, y cargo audit sobre app/src-tauri. Es informativo (continue-on-error: true) — avisa en el resumen de la Action sin bloquear el build, para no romper el pipeline por un aviso que aún no se ha triado.

Uso

Dos perfiles: el trabajador que solo instala y pega un token, y el admin que gestiona altas y bajas.

Para el trabajador

  1. Instalar el .dmg (Mac) o .msi (Windows) arrastrando a Aplicaciones.
  2. Abrir Watermelon DDNS, pegar el token que entregó el admin — se guarda solo en ese equipo.
  3. Ver Trabajador / Subdominio / IP actual en el panel. Actualizar ahora fuerza una comprobación inmediata; el log muestra "Actualizado → X" o "Sin cambios". El resto del tiempo, la app sondea sola cada 5 minutos mientras esté abierta.

Seguridad

  • Regla de oro: nunca pegar una passphrase, API key o token en el chat en texto plano. Generar en el panel web, guardar con read -rsp ...; chmod 600 en el servidor, verificar con wc -c, nunca con cat.
  • Token por trabajador: si un equipo se compromete, solo afecta a su propio subdominio — se revoca con remove + add de un token nuevo.
  • El token de Cloudflare está limitado (scoped) a Zone.DNS Edit únicamente sobre watermelonmarketing.com y nunca sale del backend.
  • El token del trabajador ya no vive en el localStorage del WebView — ver Endurecimiento de seguridad. Sigue sin ser un almacén cifrado por el sistema operativo; eso queda como mejora pendiente explicada más abajo.
  • La app tiene una Content-Security-Policy activa (antes era null) que limita a qué dominios puede conectarse y qué puede cargar el WebView.
  • El backend tiene rate limiting (30 req/min por IP en /api/*) y CORS restringido a los orígenes reales del WebView de Tauri — ver Endurecimiento del backend.
  • Transporte siempre por https://ddns.xwmkt.com con Let's Encrypt — el fallback http:// es solo para depurar, nunca para producción.
  • Tauri declara permisos mínimos (core:default, opener:default, store:default) — sin acceso a sistema de archivos ni a ejecución de comandos del sistema operativo.
  • El backend corre en el contenedor como usuario sin privilegios (node, no root), en una imagen final sin herramientas de compilación.
  • Los tokens se pueden rotar con node cli.js rotate <subdominio> sin dar de baja y de alta al trabajador.
Lo que queda deliberadamente sin resolver, y por qué

Cifrado del token por el sistema operativo (Llavero de macOS / Credential Manager de Windows): la vía natural es el crate de Rust keyring, pero su API cambió varias veces entre versiones y no logré verificar con fuentes fiables la firma exacta de sus funciones para la versión actual. Añadir a ciegas una dependencia nativa que compila distinto en macOS/Windows/Linux, sin poder probar el compilado aquí, se traduce en riesgo real de romper tu build o el CI en alguna plataforma por un detalle de API que no pude confirmar. Prefiero decírtelo claro a adivinar.

Firma de código de los instaladores (evita el aviso "Editor desconocido" de Windows SmartScreen y el bloqueo de Gatekeeper en macOS): esto no es algo que se resuelva con código — hace falta que tú obtengas un certificado de firma de Windows (de una CA) y una cuenta de Apple Developer Program (99 $/año) para notarización en macOS. Puedo dejar preparado el workflow de GitHub Actions para firmar automáticamente en cuanto tengas esos certificados, pero añadir esa configuración ahora, sin certificados reales para probarla, es exactamente el mismo tipo de cambio a ciegas que quiero evitarte en tu CI ya funcional.

Roadmap / pendientes

  • Icono en la bandeja del sistema — hecho, ver Bandeja del sistema. Queda pendiente el autostart (arrancar la app al iniciar sesión en el equipo, plugin Tauri autostart).
  • Cifrado del token a nivel de sistema operativo (Llavero de macOS / Credential Manager de Windows) — ver la nota en Seguridad sobre por qué no se implementó a ciegas.
  • Firma de código de los instaladores (Windows + notarización macOS) — requiere certificados que solo tú puedes obtener; ver Seguridad.
  • Soporte IPv6 (AAAA) además de A.
  • Rate limit — hecho, ver Endurecimiento del backend. Queda pendiente un histórico de IPs por trabajador para auditoría (más allá de last_ip/updated_at).
  • GitHub Actions para builds multiplataforma — hecho, ver Build multiplataforma automático. Queda pendiente publicar releases automáticos (adjuntar los instaladores a un GitHub Release en vez de solo subirlos como artefacto de la Action).
  • /health con last_ip agregado, para monitorizar con Uptime Kuma (ya corriendo en xwmkt).
  • Migración de esquema si la tabla crece: añadir created_at, failed_attempts.
